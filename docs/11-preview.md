# The public preview

**What this is.** A public HTTPS address with a **stable** name, on which the
whole product runs — including the live scores stream, which the quick tunnel of
T-085 cannot carry. It is where the live path gets tested in public before there
is a server (T-074).

**What it is not.** Production. The web service sleeps when nobody is looking.
`docs/09-deploy.md` is still where the product goes to live.

**Where it runs.** Render for the container, Neon for the database (D-064).
Koyeb was the original choice (D-051) and stopped being one: it was acquired in
February 2026 and its free Instance is no longer offered to new accounts.

---

## The shape, and why

A free web service is one container: 512 MB, asleep after 15 minutes without
traffic, about a minute to wake. Five containers do not fit in one, so this is
what runs and what does not.

| | Where |
|---|---|
| Web app (Next.js) | in the container, on the published port |
| API (NestJS) | in the same container, on `127.0.0.1:3001` |
| Postgres | a Neon free project, outside the container |
| Model service | **not deployed** — forecasts say `model_unreachable` |
| Redis | **not deployed** — the ingestion scheduler and live chat delivery need it |

**One port carries everything, including the stream.** Nothing in the browser
talks to the API directly: the Next.js route handlers at `/api/scores/stream`
and `/api/fixtures/:id/stream` proxy server-sent events from the API
server-side. So a single published port serves the whole product, which is
exactly what makes one free container enough — and what a quick tunnel could not
do.

**No model service, said out loud.** `MODEL_SERVICE_URL=off` is how a deployment
declares it has no model service. Every forecast is then recorded as
`model_unreachable` with that reason and the pages show it the way they already
show any unavailable forecast. Forgetting the variable still refuses to boot;
`off` is a statement, not an omission.

**No scheduler.** A container that scales to zero cannot poll a provider on a
schedule, and pretending otherwise would leave gaps that look like outages.
`INGESTION_SCHEDULE=off`, and the preview's data is whatever the database holds.

**No live chat delivery, and the preview says so.** Two independent reasons, and
either alone would be enough. There is no Redis, so the chat bus is `absent` and
`GET /health/chat` reports it (T-233). And the socket has nowhere to arrive: the
VPS routes `/me/conversations/socket` at the edge (T-234), and this deployment
has no edge — one published port, held by Next.js, which cannot answer a
WebSocket upgrade. Conversations still work here in full, because every one of
them works over ordinary requests (T-221 through T-226); what the preview does
not demonstrate is immediacy. That is also why the service sleeping — which
drops every socket — costs this preview nothing.

**The database is not Render's.** Render's own free Postgres is deleted after 30
days. A preview that dies on a schedule is worse than no preview: it fails
weeks later, silently, for a reason nobody still remembers. Neon's free project
is permanent, and it allows the two extensions the search migration creates.

## What the maintainer does by hand

Three things. An agent session does not create accounts and does not handle
secrets, so these are yours. Neither service asks for a card.

### 1. The database

1. Sign up at <https://neon.com/> and create a project in a **European** region,
   so it sits next to the container in Frankfurt.
2. Copy the connection string it shows you — the **pooled** one, and make sure
   it ends with `?sslmode=require`.

Neon runs Postgres 17 and allows `CREATE EXTENSION` for both `pg_trgm` and
`unaccent`, which is what the search migration needs (T-038). Nothing to enable
by hand: the migration creates them on the first deploy.

### 2. The service

1. Sign up at <https://render.com/> with the GitHub account that owns this
   repository.
2. **New → Blueprint**, pick `moarjmand/fmip`. Render reads `render.yaml` and
   proposes one free web service called `fmip-preview`.
3. It asks for **one** value: `DATABASE_URL`. Paste the Neon string.
   `SESSION_SECRET` is generated by Render and shown to nobody.
4. Apply. The first build takes a while; after that a push to `main` redeploys.

Everything else in `render.yaml` is already correct, including the address:
`start.mjs` takes `SITE_URL` and `WEB_BASE_URL` from the address Render assigns,
so canonical links, the sitemap, the manifest and the links in e-mails name an
address that can actually be opened. There is no post-deploy step to remember.

### 3. Check four things

| What to look at | What it should say |
|---|---|
| `/en` | the site, over HTTPS |
| the line under the heading on `/en` | `API: ok, up for Ns` — both halves of the container are alive |
| `/en/scores` | the day's tabs, and **"No fixtures on this day"** |
| view-source on `/en`, or `/sitemap.xml` | the preview's **own** address, not `localhost` |

The third is the empty database being honest rather than a page that failed:
`INGESTION_SCHEDULE=off` and `PREVIEW_SEED=off`, so the preview holds whatever
the database holds, which on a new Neon project is nothing. The fourth is D-064
working — `start.mjs` took the address from the platform, with no step to
remember.

**Two things cannot be checked from outside, and it is worth knowing why.**

*The chat bus.* `GET /health/chat` (T-233) is an **API** route, and this
deployment publishes only the web app's port — the API is on `127.0.0.1:3001`
and nothing proxies `/health`. From outside, `/health/chat` is just an unknown
path and the locale router answers `307`. The bus state does reach the log, but
only once something tries to publish: `AbsentChatBus` logs `chat.bus_absent` on
its first `publish()`, not at boot. So on a preview nobody has chatted on, the
correct expectation is **silence**, not a reading.

*The forecast state.* `model_unreachable` is recorded per fixture, and an empty
database has no fixtures. There is no page on which to see it until the preview
has data.

Neither is a fault, and neither should be written down as a step that passes
when nobody performs it.

## When something is wrong

The log is one JSON object per line. The supervisor's own lines are prefixed
`preview.`:

| Line | Meaning |
|---|---|
| `preview.address` | which address the preview believes it has, and where it came from |
| `preview.address_unknown` | nobody supplied one; links will say `localhost` |
| `preview.migrating` / `preview.fatal` | migrations ran, or failed with an exit code |
| `preview.api_healthy` | the API answered `/health`; the web app starts next |
| `preview.child_exited` | one half died, so the container is taking the other down |

That last one is deliberate (`start.mjs`): a half-running service answering
requests it cannot serve is worse than a restart.

**A first request after idle takes about a minute.** That is the free plan
waking up, not a fault.

## Building it locally

The image is the deployment, so it can be run without any of this:

```bash
docker build -f deploy/preview/Dockerfile -t fmip-preview .
docker run --rm -p 8000:8000 -e DATABASE_URL=... -e SESSION_SECRET=... fmip-preview
```
