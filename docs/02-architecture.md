# Architecture

## Principles

1. **The canonical model is the contract.** Providers, the frontend, and the
   model service all talk to our internal entity model, never to each other's
   formats.
2. **Layers are replaceable.** Any single layer can be swapped without touching
   the others: provider, hosting, model implementation, frontend.
3. **Reads are cheap, writes are deliberate.** Public read paths are cached and
   denormalised. Writes go through module services with validation.
4. **Everything time-sensitive carries its own timestamp.** Freshness is a
   first-class field, not an afterthought.

---

## Module boundaries

Eleven modules, from the blueprint's section 14.3. In Phase 1 they are NestJS
modules inside one deployable (D-011).

| Module | Responsibility | Owns tables |
|---|---|---|
| `ingestion` | Fetch from providers, normalise, resolve identity | `provider_mapping`, `ingest_run` |
| `catalog` | Competitions, seasons, teams, players, venues | `competition`, `season`, `team`, `person`, `player_spell`, `venue` |
| `fixtures` | Matches, incidents, lineups, statistics, coverage | `fixture`, `incident`, `lineup`, `fixture_stat`, `coverage_profile` |
| `standings` | Tables, groups, brackets, form | `table_row`, `stage` |
| `forecast` | Contract with the model service, forecast versions | `model_version`, `input_snapshot`, `forecast`, `evaluation` |
| `identity` | Users, credentials, sessions, permissions | `user`, `credential`, `session`, `role` |
| `profile` | Profiles, privacy, following, favourites | `profile`, `followed_entity`, `privacy_setting` |
| `predictions` | User predictions, locking, settlement | `user_prediction`, `prediction_version`, `settlement` |
| `reputation` | Performance Rating, Career Points, leaderboards | `rating_snapshot`, `points_transaction`, `leaderboard_entry` |
| `search` | Entity and text search | — (index) |
| `admin` | Coverage, config, moderation, audit | `audit_log`, `config` |

**Rule:** a module may import another module's *public service interface*. It may
never import another module's repositories, entities, or internals. Cross-module
data access goes through the owning module.

## The adapter layer

The single most important isolation boundary in the system.

```
packages/ingestion/
  adapters/
    api-football/       # provider-specific fetch + map
    football-data-org/
    highlightly/
    _contract.ts        # the interface every adapter implements
    _fixtures/          # recorded provider responses for contract tests
  normalise/            # provider-neutral shaping
  resolve/              # external id -> internal uuid
```

Every adapter implements the same interface and is verified by contract tests
running against recorded responses. Adding or replacing a provider is one
directory plus a config change — no other file in the repository moves.

## Identity resolution

Names are not identifiers. The rule from the blueprint (1.3) is enforced
structurally:

- Every entity has an internal UUID, generated by us.
- `provider_mapping (provider, external_id, entity_type, internal_id)` is the
  only place a provider ID appears.
- Localised names and aliases are attributes, never keys.
- An unresolved entity is queued for review, never guessed into an existing one.

## Coverage model

Not every competition has the same data depth. Each `(competition, season)` has a
coverage profile listing which modules are supported. The API returns a coverage
state with every module payload:

`available` · `limited` · `not_supplied` · `delayed`

The UI renders only supported modules and labels the rest. Empty placeholders
that imply coverage are a bug, not a styling issue.

## Live update path

1. Ingestion writes match state to Redis and Postgres.
2. On change, it publishes to a Redis channel.
3. The SSE gateway fans out to subscribed clients per fixture or per date view.
4. Each payload carries `last_updated_at`; the client shows staleness when the
   threshold is exceeded.
5. On reconnect, the client requests a snapshot before resuming the stream.

Polling is the fallback, not the design.

## Forecast versioning

Forecasts are immutable records:

```
input_snapshot  →  model_version  →  forecast  →  evaluation (post-match)
```

Stored: probabilities, expected goals, score matrix summary, leading factors,
data completeness, computation time. Comparing two versions is how the match
centre explains what changed after lineups were confirmed.

---

## Reputation reproducibility

`Performance Rating` must be recomputable from `user_prediction` +
`settlement` + the configured formula alone. The formula and its thresholds live
in config, are versioned, and every rating snapshot records which formula version
produced it. This is what makes an admin able to answer "why is my rating this
number".

---

## What is deliberately absent in Phase 1

No message broker beyond Redis. No Kubernetes. No microservice mesh. No GraphQL.
No event sourcing. Each of these can be introduced later behind the existing
module boundaries if a real need appears — and none of them is needed to serve
the Phase 1 scope well.
